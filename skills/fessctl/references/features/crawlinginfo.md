# Crawling Info (fessctl `crawlinginfo`)

## What it is

Crawling Info is the per-session metadata produced by Fess every time a crawl
runs. The Admin UI exposes it under **System → Crawling Info**, where each row
represents a single crawl session identified by its `session_id`. The page is
intended for observation and post-mortem analysis, not for authoring.

Each session record identifies one crawl run: its `session_id`, a `name`,
when it was created and when it expires. The crawler writes it itself; users do
not populate it. The counters and phase timestamps the crawler keeps per
session are separate records that the admin API does not return.

Because rows are produced automatically by background scheduler runs, the
`fessctl crawlinginfo` surface has no `create` or `update` verb — those
operations are not exposed by the underlying admin API and would be
meaningless for crawler-emitted telemetry. You can list sessions, fetch one
by ID, delete stale records to free up storage (one by one, or all but the
running ones with `delete-all`), and, on Fess 15.10 or later, show the
progress of the crawls that are running now with `progress`.

## When to use

- Monitor an in-flight crawl: `progress` shows each running crawl with the
  number of documents processed so far (Fess 15.10+); list recent sessions to
  see whether the scheduled crawler started, and which phase it is currently in.
- Post-mortem on a failed crawl: fetch the row for the failing `session_id`
  to see when the session was created and when it expires, then read the
  details in `joblog`.
- Capacity / housekeeping: periodically delete old or expired session records
  so the `.crawler` indices do not grow without bound.
- Correlate with `joblog`: combine the script-level run information from
  `joblog` with the session ids in `crawlinginfo` to tie a scheduler invocation to
  its crawl session.

## Subcommand surface

| Subcommand | Purpose |
| --- | --- |
| `list` | Page through crawling-info rows (`--page`, `--size`, `--output`). |
| `get` | Retrieve one row by `crawlinginfo_id` (`--output`). |
| `delete` | Remove one row by `crawlinginfo_id` (`--output`). |
| `delete-all` | Remove every session except the running ones. Asks for confirmation unless `--yes` (`--output`). |
| `progress` | Show the running crawls and how far they are (`--output`). Needs Fess 15.10 or later. |

There is no `create` and no `update` subcommand, because crawling-info rows
are generated by the crawler itself. Always reconfirm with
`fessctl crawlinginfo <sub> --help`.

## Resource JSON shape

The admin API returns rows under `response.logs` (list) or `response.log`
(single). Fields are server-populated.

```json
{
  "crud_mode": 0,
  "id": "AY1n...e1Q",
  "session_id": "20260503120000000",
  "name": "system",
  "expired_time": "1717315200000",
  "created_time": 1714723200000
}
```

Notes:

- `id` is the OpenSearch document id; pass it as `crawlinginfo_id` to `get`
  and `delete`.
- `session_id` identifies one crawl run (the timestamp-style id also shown in
  the `joblog` `script_result`); `name` is the name given to the crawl
  session, `system` when none was set.
- The row carries only `id`, `session_id`, `name`, `expired_time` (a string)
  and `created_time` (a number), plus a constant `crud_mode`. The per-session counters and phase timestamps the crawler
  keeps are separate parameter records that the admin API does not return,
  so there is no `value` field.
- `expired_time` is the epoch-millis after which the row is eligible for
  automatic GC by Fess.

## Progress JSON shape

`progress` returns the running crawls under `response.progress` (ordered by the
name of the crawl configuration) and their number in `response.total`.
`--output text` prints them as a table; json and yaml print the whole response.

```json
{
  "response": {
    "status": 0,
    "total": 1,
    "progress": [
      {"config_id": "Wabc123", "name": "Example Site", "count": 4200,
       "last_count": 10000, "updated_time": 1738144800000, "percent": 42}
    ]
  }
}
```

- `count` is the number of documents processed so far (access results for web
  and file crawls, indexed documents for a data store crawl). `last_count` is
  the count of the previous *completed* crawl of the same configuration, `0`
  when there is none.
- `percent` is `count` as a percentage of `last_count`, capped at 99 until the
  crawl completes. **The key is left out when there is no previous count** (the
  first crawl of a configuration); the text table shows `-` then.
- With no crawl running the list is empty (`No running crawls found.`).
- A crawl that finished or was stopped drops out of the list about 30 seconds
  after its last update, so a just-stopped crawl can still show up briefly.
- The numbers are written by the crawler every crawl interval, so `count` moves
  in steps and can lag the real crawl.

## Relationships

- Produced by `scheduler` jobs that invoke the crawler (default jobs:
  `Default Crawler`, `Default File Crawler`, etc.).
- Complementary to `joblog`: `joblog` records the script-level run
  (start/end, exit status of the scheduled job), while `crawlinginfo`
  records the crawl sessions.
- Consumes data emitted by `webconfig`, `fileconfig`, and `dataconfig`
  targets that the scheduled crawler walked.
- Stored alongside other crawler runtime state in the `.crawler` index
  family; deleting a row does not undo any indexed search documents.

## Gotchas

- **No create or update.** There is no `fessctl crawlinginfo create` and no
  `fessctl crawlinginfo update`. Do not look for them, and do not invent
  flags. The CLI exposes `list`, `get`, `delete`, `delete-all` and `progress`.
- **`progress` needs Fess 15.10.** Older servers have no such endpoint and the
  command fails with the server's error. `delete-all` exists on every
  supported version.
- **`delete-all` keeps running crawls only.** It deletes every other session
  and its parameters, with no age threshold; the sessions of a crawl that is
  running are kept (verified while a crawl ran). The deleted rows can still be
  listed for a few seconds, until the index refreshes. Like every admin API
  call it needs an access token with admin API permission; a token without it
  is answered with `Unauthorized request.` and exit code 3.
- Rows accumulate across every scheduled crawl run. On busy installations
  this index grows quickly; plan periodic cleanup via `delete`.
- The `expired_time` field drives Fess's own automatic garbage collection.
  Manual `delete` is only needed when you want to reclaim space sooner than
  the configured retention window.
- `delete` removes a single row by id, not a whole `session_id`. To purge
  an entire crawl session you must iterate over every row that shares the
  session id, or use `delete-all` to clear everything but the running ones.
- `get --output text` titles its table with `-` (it looks up a `job_name`
  field that crawling-info rows do not have); the title carries no
  information, use the `session_id` row.
- Deleting a crawling-info row does not delete the indexed documents
  produced by that crawl; it only removes the telemetry record.

## Examples

List the most recent crawling-info rows:

```bash
fessctl crawlinginfo list --page 1 --size 20
```

Fetch a single row by id:

```bash
fessctl crawlinginfo get AY1n0abc_examplee1Q --output json
```

Show the running crawls, then clear the old sessions:

```bash
fessctl crawlinginfo progress
fessctl crawlinginfo progress --output json | jq '.response.progress[] | {name, count, percent}'
fessctl crawlinginfo delete-all --yes
```

Bulk-delete every expired session row using `--output json | jq | xargs`:

```bash
fessctl crawlinginfo list --size 1000 --output json \
  | jq -r --argjson now "$(date +%s000)" \
      '.response.logs[] | select(.expired_time != null and (.expired_time | tonumber) < $now) | .id' \
  | xargs -n 1 -I {} fessctl crawlinginfo delete {}
```
